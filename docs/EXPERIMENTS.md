## 2. 事故①：防御规则污染（"假 L1"）

- defense.py 用 `.bak` 备份恢复切换规则集；多次 L0→L1 切换后 `.bak`
  被训练规则覆盖，"恢复默认"静默恢复成训练规则（`|| true` 吞错）。
- 后果：t0 及全池长期以 4 条训练规则冒充"L1 完整默认规则集"。
- 数据对比（同一 bee 同一路径部署）：
  - 假 L1（训练规则）：Falco 告警 **6433 条**/10 分钟（proc=bee 全部命中
    "Training Execution from Tmpfs"——bee 从 /tmp 运行，子进程祖先链全触发）
  - 真 L1（25 条默认规则）：告警 **0 条**/10 分钟，底噪 0
- 修复：双等级都推送明确 asset（falco_rules_default.yaml 63723B 存档），
  删除 .bak 机制。
- 推论：在更严的训练规则下毕业的技能/Router，在真 L1 下生存指标只会更好。

## 3. 事故②：任务响应死局（四连环根因）

verify_bee 两次部署 tasks_done=0/2。归因链：

1. Router 训练任务模型是"episode 固定任务类型 + 对齐动作计数"
   （tasks 可到 142），部署是"离散指令 pending 至完成"；
   rfeat[0] 训练时恒 1.0，部署时 0/1 切换 → 分布外输入。
2. C 技能 BC 语料只映射因果链 {1,2,5}，communicate(4) 零样本。
3. SKILL_TASK_ACTIONS["C"]=(EXECUTE_TASK,)，ES 不奖励 4 → 扰动压掉。
4. feat[1] task_progress：BC replay 填 0→1 递增，bee 端恒 0 →
   4 的全部样本落在分布外。

修复与效果（真实 VM 180 步 argmax 实测）：

| 版本 | action=4 次数 | 动作分布 |
|---|---|---|
| 旧 skill_c | 0 | {1:全部} |
| BC+4样本(3) + ES v2 | 0 | {1:173, 2:1, 5:6} |
| BC+4样本(8) feat[1]=0（现 skill_c.pt） | **62** | {1:75, 2:27, 4:62, 5:16} |

结论：特征维度训练↔部署对齐 > 样本量 > ES 调参。

## 6. 工程坑（复用价值）

- `pkill/pgrep -f <模式>` 会匹配自身命令行 → 用 `bee w[e]i` 式字符类。
- 后台子进程必须 `nohup ... & disown`（或 setsid），否则随任务组回收。
- watchdog 的存活探测模式不能出现在任何长寿父进程的命令行里。
- Python/Rust 走 pipe 块缓冲，日志静默 ≠ 没在跑（看进程与检查点 mtime）。
- ES 训练必须保存历史最佳 base；振荡地形上终点 base 不可信。

## 9. 联合对抗评估（2026-07-30 21:10，冻结权重 router_v7_best）

每档 3 episode × 200 步，真机 Falco+响应器波次：

| 档 | 波次强度 | alive | tasks | alerts | elim |
|---|---|---|---|---|---|
| L1 标准级 | 0.4 | 200/200/200 | 1.7 | 0 | **0** |
| L2 施压级 | 0.7 | 200/200/200 | 1.7 (4,1,0) | 0 | **1.7 (3,1,1)** |

### 归因

1. **复活机制是 L2 满血的唯一原因**。L2 波次加密后消杀命中 5 次/3ep，
   但 bee 全部 200 步满血——D 技能的 kill_chain（12 次）+local_copy（6 次）
   在被打后完成了复活。没有复活链，L2 存活率会是 ~33%（ep0 被打 3 次）。
2. **剂量-反应关系明确**：干活最多的 ep0（tasks=4）暴露最大（elim=3），
   收敛的 ep2（tasks=0）只被扫到 1 次。Router 的"无任务静默"策略在
   高压下自发产生了降暴露效果。
3. **action=4 communicate 177 次/3ep**（C 被选中时 ~34% 出 4）：
   靶场 Falco 不看网络，0 告警；但在真实 NDR 视角下这个报联频率
   本身就是可检测模式。C 技能的 4 频率（BC 头 34%）偏高，后续可 ES 压到
   "按需报联"（pending report 才出）。
4. **已知死穴未爆但持续失血**：落点 /tmp/bee_deploy 在响应器 scan 范围，
   每波必被看到、靠复活硬扛。根治要迁落点（$HOME 伪装系统文件路径），
   这是部署形态问题，不是权重问题。

### 达标判定

L2 存活率 100%（≥80% 线）、tasks 1.7（≥1.0 线）——**goal 达标**。
L3（多波随机消杀 1.0）未测，留作下一轮。

## 13. C2 加密通讯通道（2026-07-31，基础版全链路达成）

**AES-256-GCM 手写实现**（bee/src/aes_gcm.rs，零依赖红线）：
FIPS-197 附录C 块加密向量 + NIST GCM 向量 + 解密往返 + 篡改必拒，全过。

**通道**：内网 HTTP 伪装 + AES-256-GCM 报文级加密（AAD=agent id，
96-bit 标准随机 nonce，每报文独立）。服务端 training/c2/hive.py
（pycryptodome），bee 端 c2.rs（手写最小 HTTP+GCM+base64）。

**端到端验证（t0 实战）**：
① 推→拉→执行→回传：TASK RECV report@376 → DONE@389 → hive 收明文
② 信道无明文：{"v":1,"data":base64(nonce‖ct‖tag)} 信封
③ AEAD：tag 篡改 403 必拒；无关密钥 403 必拒
④ 密钥轮换窗口：current(v2)+previous(v1) 均可解，无关密钥拒

**关键坑**：pycryptodome AES.MODE_GCM 默认 nonce 是 16 字节（非标准
96-bit），与手写 Rust（12 字节 J0=nonce‖1）不兼容——发送方向 MAC
全错。修：显式 nonce=os.urandom(12)。教训：GCM 实现互操作，nonce
长度是首要对齐项。

## 21. 提权实战（2026-07-31，靶场 VM 收紧 sudo）

**环境**：range 常用命令 NOPASSWD（journalctl/systemctl），其他 sudo 要密码
（bee 不知道）。弱点：/etc/passwd 666、SUID find、cron.d 777。
falco 提权检测（auditd 无网装不上）：passwd_write/find_exec/cron_write/su_sudo 4 条。

**提权路径验证**：
- 路径1（写 /etc/passwd 加 root 用户）：现代 Ubuntu 密码分离到 /etc/shadow
  （640 不可写），passwd 写用户也 su 不进——**不可行**。
- 路径3（cron.d 写 root 任务）：cronie 要求 cron.d 文件 root 拥有，range 写的
  被拒——**不可行**。
- 路径2（SUID find + python3 os.setuid(0)）：**root 提权成功**（dash/bash 降权
  由 python 不降权绕过），但**被 falco privesc_find_exec 抓到**（find 工具模式）。

**隐蔽提权（关键成果）**：**SUID python3 + os.setuid(0)**——
python3 不在 find 规则里，euid 变化（setuid syscall）falco 没配规则
（正常程序也调 setuid 误报高）——**既提权到 root 又 falco 抓不到**。

**核心洞察**：提权检测的两大盲区——①载体多样性（几十种 GTFOBins，
规则只能盯已知模式 find，换载体即规避）②euid 变化（setuid 是提权根本
暴露，但正常程序也调 setuid，规则误报高所以不配）——**隐蔽提权 =
规则外 SUID 载体 + euid 直接 setuid(0)**。

**提权自主化**（§21 续）：privesc 做成 bee 自主能力（不再手动模拟）——
新任务类型 privesc（C2/task.txt 下发），bee 执行 privesc_script：
扫描 SUID 误配置（python/perl/ruby/node 优先=不降权可靠载体+规则外隐蔽，
GTFOBins 兜底）→ os.setuid(0)。判定：输出含 uid=0 即提权成功。
实测：TASK RECV privesc step=0 → **TASK DONE privesc step=1**（一步自主
提权到 root，t0 的 SUID python3.12 弱点被 bee 自主发现利用）。
不改动作空间不重训技能头（privesc 是任务类型不是技能动作）。

本机 GLM-4.5-Air（llama-server :8080）。纪律：**LLM 只提名，确定性核验器处置**
——每条提名须过硬事实（隐藏路径可执行体/无安装记录/进程存续），

### 缺陷与修正

1. responder_v2 scan 包装层曾把输出按空白拆碎（`for line in $(...)` 经典 bash 坑）——

2. 司命猎手过度杀伤：把 bee 的 sh -c 动作臂链（父=sh）一并判死——sh 链太通用，

3. falco 告警 → journal 延迟 60~80s 依旧（§22 已记），LLM 猎手不受影响（读状态不读告警）。
